# cyk-impl-from-plan

`cyk-impl-plan-create` が作成した実装計画に沿って実装を進め、その過程で判明したことを Issue と計画ファイルに反映していくスキル。

このスキルの本質は「実装」と「記録」が抱き合わせであること。**Step の実装を終えたその場で記録する**（すべて実装してからまとめて書かない）。実装中に判明したことは、計画時点の Issue サマリーではカバーできていない情報であり、それを残さないと次に同じ調査コストを払うことになる。

## 反映先の使い分け

記録先を混同しない。3つの反映先は役割が異なる。

| 反映先 | 何を書くか | 性質 |
| --- | --- | --- |
| Issue コメント | どんな作業をしたかのトレース | **時系列**。ある程度の経緯を含んでよい |
| `docs/issues/<N>/` の計画ファイル | 計画通りにならなかった箇所の修正、Step の ✅ | **現時点の正**。上書き |
| Issue 本文（サマリー） | 変化した完了条件 | **現時点の正**。上書き |

ボリュームが小さく1つのコメントにまとめる場合のみ、コメントが時系列と現時点の正を兼ねる（Step 1・4・7 を参照）。

特に **完了条件の変化は Issue 本文に反映する**こと。コメントに書いても、次に Issue を開いた人（次のセッションを含む）は古い完了条件を読んでしまう。

## 手順

### 1. Issue と実装計画の読み込み

`$ARGUMENTS` から Issue 番号または URL を解決する。指定がなければユーザーに確認する。

```bash
gh issue view <ISSUE番号> --json number,title,body,comments,url
```

続いて実装計画を読み込む。

- `docs/issues/<issue番号>/index.md` を読む
- 分割構成（`NN-<topic-slug>.md`）の場合は各ステップファイルも読む
- 計画が存在しない場合はここで停止し、`cyk-impl-plan-create` の実行をユーザーに促す

読み込んだら、未完了（✅ が付いていない）の Step 一覧をユーザーに提示し、着手を確認する。

あわせて、**コメントの粒度をここで決める**。Step ごとに別コメントを立てるか、1つのコメントにまとめるかを着手前に確定させ、Step ごとに判断し直さない。

粒度は **Step 数ではなく作業の大きさ**で決める。Step が多くても、小さな作業を Step ごとに投稿すると、読み手にも承認するユーザーにも手間が増えるだけになる。

| 粒度 | 目安 | 記録の仕方 |
| --- | --- | --- |
| まとめのみ | 関心事が1つで作業量が小さく、詳細が計画ファイル・ドキュメント・コードに残る（例: テスト環境の導入、設定の追加） | Step ごとのコメントは立てない。Step ごとの記録は計画ファイル（ズレの反映・✅）で行い、全 Step 完了後に `## 実装完了まとめ` のコメントを1つだけ投稿する |
| 1つのコメントにまとめる | まとめのみでは経緯が残らないが、Step ごとに立てるほどの量はない | 1つのコメントを Step ごとに育てる |
| Step ごとに立てる | 作業量が大きい、Step ごとに関心事が違う、検証で試行錯誤や不具合の発見が見込まれる | Step ごとにコメントを立てる |

迷ったら軽い方を選び、決めた粒度を着手時にユーザーに一言で伝える。ユーザーの指示があればそちらに従う。

**1つのコメントにまとめる場合も、記録するタイミングは変わらない。** Step ごとに記録する（Step 4 の手順で同じコメントを育てる）。すべて実装してから最後にまとめて書くのではない。変わるのはコメントの数だけで、記録の時点ではない。

### 2. Step の実装

未完了の Step を先頭から順に実装する。全 Step を通しで進めるが、**1 Step ごとに Step 3〜5 の記録処理を挟む**。次の Step に進む前に必ず記録を終わらせる。

実装中は以下を意識する。

- 計画に書かれた具体名（ファイルパス・関数名・設定キー）に従う
- 計画と実際のコードが食い違った場合、**その場で立ち止まる**。勝手に方針を変えず、後続の Step 3 で計画側を直す
- 手作業が必要な項目（環境変数の設定、外部サービス側の設定変更など）はユーザーに依頼し、完了を待つ

**動作確認・検証の Step も、コードを書く Step と同じように記録する。** 手作業でユーザーと対話しながら進めた Step は、差分が残らないため記録を飛ばしやすい。しかし再現手順・実測値・そこで見つかった不具合は**その場でしか得られない情報**であり、記録しなければ次に同じ検証コストを払うことになる。

検証 Step では特に以下を意識する。

- **検証中に得た事実はその場で集める。** 対話で進むため結果が会話に散らばる。「どのケースで何が起きたか」を都度メモしていく
- **失敗したケース・想定と違ったことを必ず残す。** 検証が全部一発で通ることは少ない。試行錯誤（環境が思い通りにならない、テストデータの作り方を変えた等）こそ次回の再現に効く
- 検証で不具合が見つかり Step を追加した場合も、**まず検証 Step 自体を記録してから**追加 Step に進む（発見の経緯が時系列から欠けないようにする）

検証で不具合が見つかった場合、本 Issue 内で直すか別 Issue に切り出すかをユーザーに確認する。本 Issue 内で直す場合は計画ファイルに Step を追加し（Step 3 の要領で）、通常の Step と同じ手順で実装・記録する。

### 3. 計画とのズレを計画ファイルに反映

Step の実装が計画通りに終わったなら、この節はスキップして Step 4 に進む。

**ただし「結果が計画通り」と「手順が計画通り」は別。** 検証 Step では、確認できた結果は計画通りでも、そこに至る手順が違うことが多い（計画に書いた投入方法が使えず別経路を採った、前提となる環境操作が追加で必要だった等）。この場合は**ズレとして扱い、計画ファイルを実際の手順に書き換える**。計画ファイルは次に同じ検証をする人が読むものであり、動かない手順が残っていると再現できない。

計画通りにならなかった場合、**計画ファイル側を実際に合わせて上書き修正する**。

- 実際に行った手順に書き換える（計画ファイルは「現時点の正」であり、変遷の記録場所ではない）
- 後続 Step の前提が崩れている場合は、後続 Step の記述も併せて修正する
- 修正は**実際の diff**をユーザーに提示し、承認を得てから書き込む。変更点の要約で代替しない。要約では**削除した行が見えず、意図しない欠落に気づけない**（計画ファイルは上書き運用のため、節が丸ごと消えても後から復元できない）

破棄された当初の計画そのものは計画ファイルに残さない。「なぜ変えたか」は Step 4 の Issue コメント側に時系列として残る（粒度が「まとめのみ」の場合は、Step 7 のまとめの「計画から変わった点」に残す）。

### 4. 作業内容を Issue コメントに追記

粒度が「まとめのみ」の場合はこの節をスキップする（Step 7 のまとめだけを投稿する）。

Step の実装内容を Issue コメントとして記録する。**作業のトレースが目的**なので、ある程度の時系列・経緯を含んでよい。

コメントの形：

```markdown
## Step <N>: <Step タイトル>

<このStepで何をしたかを1〜2行。読者がぱっと見て何の話か分かるようにする>

### 詳細

<変更したファイル・検証結果など。ファイルパス・関数名などの具体名で書く>

### 計画とのズレ

<計画通りだった場合はこの節ごと省略>
- <計画: 〜 → 実際: 〜。理由を1行で>
```

動作確認・検証の Step の場合は `### 詳細` を以下に置き換える。

```markdown
### 確認したこと

| ケース | 結果 |
| --- | --- |
| <確認したケース> | <確認済み / 実測値。想定と違った場合はその内容> |

### 検証中に判明したこと

<想定通りだった場合はこの節ごと省略>
- <検証環境の制約・テストデータの作り方を変えた等、次回の再現に必要なこと>
- <見つかった不具合と、その対応（別 Step を立てた場合はその旨）>
```

書き方の基準：

- **見出しの直後は概要から書く。** いきなり箇条書きやコード片を始めない。読者はまず「何の話か」を知る必要がある
- 概要と詳細を同じ塊に混ぜない。詳細は `### 詳細` 以下の節に落とす
- **概要の1〜2行を除き、コメント全体を箇条書きで書く。1項目1行。** `### 詳細` に限らず、独立した節を立てた場合もその中身は箇条書きにする（節を分ければ段落で書いてよい、ではない）
- **未来の予定を書かない。** 「Step N で確認する」「後で対応する」「実機確認は Step N なのでチェックは付けない」はコメントの役割ではない（コメントは実施済みのトレース）。予定は計画ファイル側の該当 Step に書く
- **ユーザーへの報告をコメントに混ぜない。** 「〜なのでチェックはまだ付けません」のような進行の断り書きは会話で伝えれば足りる。コメントには実施した内容だけを書く
- 同じことを別の言い方で二度書かない。`### 詳細` に書いた事実を後続の節で言い換えない
- 差分が1〜2行程度なら、コード片を再掲しない。何をどう変えたかを文で書けば足りる
- 試行錯誤して破棄した経路は **1行に圧縮して残す**。「A を試したが〜のため B にした」の粒度で足り、A の詳細な手順は書かない
- 「なぜそうしたか」は1行。段落で書かない
- 計画ファイルに書いた内容をそのまま転記しない。コメント側は「どう進んだか」、計画ファイル側は「どうなったか」

投稿前に、コメント本文をユーザーに提示して承認を得る。

```bash
gh issue comment <ISSUE番号> --body-file <一時ファイル>
```

Step ごとに追記していくのが基本。ただし以下の場合は、追記せず既存コメントを上書き修正する。

- **Step 1 でまとめる方針にした場合** — 全 Step を通して1つのコメントを育てる。Step を終えるたびにその Step の節を書き足して上書きする
- 直前のコメントと内容がまとまる場合（同じ関心事の続き、直前 Step の訂正など）

直前の自分のコメントを上書きするだけなら `--edit-last` でよい。

```bash
gh issue comment <ISSUE番号> --edit-last --create-if-none --body-file <一時ファイル>
```

**ただし、まとめる方針で Step をまたいで育てる場合は `--edit-last` を使わない。** `--edit-last` は「自分の最後のコメント」を編集するが、`gh` はユーザー本人の権限で動くため、AI が書いたコメントとユーザー自身が書いたコメントを区別できない。Step の合間にユーザーがコメントを付けると、次の上書きが**そのコメントを破壊する**。

そこで**最初の投稿でコメント ID を控え、以降はその ID を明示して上書きする**。

```bash
# 初回：投稿してIDを控える（返る URL 末尾の issuecomment-<ID> でもよい）
gh issue comment <ISSUE番号> --body-file <一時ファイル>
gh issue view <ISSUE番号> --json comments --jq '.comments[-1].id'

# 2回目以降：控えた ID を明示して上書き
gh api -X PATCH /repos/{owner}/{repo}/issues/comments/<ID> -F body=@<一時ファイル>
```

上書きするか追記するかは、**読み手がトレースとして追えるか**で判断する。判断に迷う場合はユーザーに確認する。

まとめる場合も、**1つのコメントの中では Step ごとの節（`## Step <N>: <タイトル>`）を保つ**。節を溶かして1つの説明にしない。どの Step で何をしたかが追えなくなる。

まとめる方針では1つのコメントを上書きし続けるため、そのコメントは時系列のトレースであると同時に現時点の正も兼ねる。**この場合に限り、古い記述が実装と食い違ったら上書きして直してよい**（Step ごとに立てたコメントは従来どおり後から直さない）。

### 5. 完了条件の変化を Issue 本文に反映

Step の結果、Issue の完了条件が変化した場合のみ実行する。変化していなければスキップして次の Step に進む。

「完了条件の変化」とは、**この Issue が「終わった」と言える基準が変わること**。以下は該当する。

- やるべきことが増えた・減った
- 受け入れ基準の内容が変わった
- スコープの境界が動いた（別 Issue に切り出す、この Issue に取り込む）

単なる実装手段の変更（同じ完了条件を別の方法で満たした）は該当しない。それは Step 3・4 で記録済み。

反映は **Issue 本文の該当箇所を上書き**する。旧条件は打ち消し線などで残さない（Issue 本文は常に現時点の正。変遷はコメント側にある）。

変更前後の**実際の diff** をユーザーに提示し、承認を得てから反映する（要約で代替しない）。

```bash
gh issue edit <ISSUE番号> --body-file <一時ファイル>
```

### 6. 計画ファイルの Step に ✅ を付ける

Step 3〜5 の記録が完了したら、計画ファイルの該当 Step 見出しに ✅ を付ける。

```
## Step 1: リファクタリング ✅
```

分割構成の場合は `index.md` 側のステップ一覧と、分割ファイルの先頭見出しの両方に付ける。

ここまで終えたら次の Step に戻る（Step 2 へ）。

### 7. 全 Step 完了後のまとめ

粒度が「まとめのみ」の場合は、Issue ではなく計画ファイルの全 Step に ✅ が付いていることを確認し、下の確認コマンドは飛ばしてまとめコメントを投稿する。

まとめに入る前に、**各 Step の記録が揃っているか Issue を確認する**。見るのはコメントの数ではなく、**どの Step の内容も書かれているか**。まとめる方針なら1つのコメントの中に全 Step の節が揃っていること、Step ごとの方針ならそれぞれのコメントがあることを確認する。

```bash
gh issue view <ISSUE番号> --json comments --jq '.comments[].body' | grep -E '^## Step '
```

計画の Step 番号と照合し、記録が無い Step があればここで補う（まとめを書く前に投稿・上書きする）。**手作業の検証 Step は差分が残らないため抜けやすい。** 計画ファイル側は ✅ が付いていても、Issue に記録が無ければトレースとしては欠落している。

すべての Step の記録が揃ったら、まとめコメントを Issue に追記する。

各 Step のコメントは時系列のトレースであり、**まとめはそれを読まなくても現状が分かるもの**にする。時系列の再要約にしない。

**まとめる方針の場合は、まとめコメントを別に立てず、同じコメントの末尾に `## 実装完了まとめ` の節として書き足す。** 直上に全 Step の内容があるため、別コメントにすると同じことを二度読ませることになる。

まとめを書いた後（`cyk-gh-flow` の ⑤ 動作検証・⑥ レビュー修正など）に記録が発生した場合は、**まとめる方針でもそこからは新しいコメントを立てる**。まとめ以降は「実装が一区切りした後の出来事」であり、時系列として分かれている方が追いやすい。

```markdown
## 実装完了まとめ

### 最終的にやったこと
- <Issue 全体として何が実現されたか。3〜5行>

### 計画から変わった点
- <Step ごとのズレのうち、後から効いてくるものだけ。無ければ「なし」>

### 残課題
- <未対応・別 Issue 化すべきもの。無ければこの節ごと省略>
```

投稿前にユーザーに提示して承認を得る。

残課題がある場合は、別 Issue を立てるかユーザーに確認する（`cyk-gh-issue-create` を使う）。

## やらないこと

- コミット・プッシュはしない（ユーザーがタイミングをコントロールする）
- PR 作成は行わない（`cyk-gh-pr-create` の役割）
- 実装計画の新規作成は行わない（`cyk-impl-plan-create` の役割）
