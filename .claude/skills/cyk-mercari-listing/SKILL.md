# メルカリ出品準備の取りまとめ

ユーザーとの対話はこのメインセッションで行い、商品ごとの原稿作成は `cyk-mercari-item-preparer` に任せる。原稿準備は並行、メルカリへの入力はアプリ経由で直列に進める。

## 現在の実装状況と実行範囲

`~/src/github.com/cyokodog/cyk-mercari-post` の `docs/api.md` とREADMEを読み、実行時の `GET /api/health` の能力一覧、API契約、実装を確認する。サーバーの起動だけを、全機能が利用可能な証拠にしない。商品保存・カテゴリー検索・入力処理は別の能力として判断する。

- 起動確認が成功しても、商品保存や入力機能の提供を意味しない。能力一覧がAPIに実装された場合はその応答も確認し、確認できない能力を有効と推測しない。
- `mercariAdapterVerified` が `false` なら、原稿準備とアプリ内保存までにとどめる。未検証アダプターを自動で有効化したり、実画面への反映を検証済みと報告したりしない。
- 必要なAPIが未実装・接続不可なら、その工程で停止する。原稿を会話に返すことはできるが、アプリへの保存済み・メルカリへの入力済みとは報告しない。
- APIのパス、カテゴリーID、商品ID、認証方法、リクエスト形式を提案段階の例から決め打ちしない。実装済みの契約に従う。
- APIの不足を、AIによるメルカリの直接UI操作や無断のローカルファイル保存で穴埋めしない。

## 役割と停止条件

| 担当 | 責任 | 行わないこと |
| --- | --- | --- |
| メイン | 商品の振り分け、担当への入力、不明点の集約、ユーザー確認、アプリへの保存・入力依頼、結果の確認 | 全商品の画像を各担当へ渡す、未承認のメルカリ入力 |
| 商品担当 | 担当する1商品の画像・補足・既存原稿から、根拠つきの原稿と質問を返す | ファイル変更、原稿の永続保存、ブラウザ入力、ユーザーへの直接質問、別商品の推測 |
| cyk-mercari-post | 実装済みの範囲で画像・原稿・状態を保存し、Chrome拡張から入力して結果を返す | AIサービスのAPI連携、今回の範囲外の操作 |

- メルカリに反映する対象と内容はユーザーの明確な承認を得る。準備・アプリ内保存の依頼をメルカリ入力への承認と解釈しない。まとめて承認された場合は、その商品IDと原稿の版を対応させ、同じ内容への二重承認は求めない。
- 「出品する」は押さない。「下書きに保存する」も今回は操作しない。メルカリの下書き保存は将来の追加機能で、現時点では未対応。
- 対象は画像・商品名・カテゴリー・商品の状態・商品の説明の5項目と、商品の特徴（サイズ・カラー・汚れ・破れ・臭いなど）、ユーザーが指定した価格。特徴はAPIの `attributes`（欄名→メルカリの選択肢の表示名）、価格は `price` で保存する。配送はメルカリ側の既定値を使い、ブランド欄などの他項目は依頼しない。

## 1. 商品を分け、対応表を作る

1. 入力された画像パス・フォルダ・補足説明、または既存の商品IDを確認する。画像が会話添付だけでローカルパスが不明なら、原稿作成は続けられるが、保存・アップロードの前にファイルの場所を確認する。
2. 商品ごとのフォルダなど、ユーザーが指定したまとまりを優先する。画像だけでは商品の境界が不明なら、分け方を聞いてから担当へ渡す。同じ商品の別角度を別商品にしたり、別商品をセット売りにまとめたりしない。
3. 商品ごとにID・画像の順序・補足・既存原稿を対応させる。アプリに既存データがある場合はそのIDを使い、IDを新規作成する場合は登録APIの返り値を使う。API未実装時の会話内の仮IDは `temp-01` のように明記し、アプリに保存されたIDと扱わない。
4. 画像の取り違えを防ぐため、ID・仮の商品名・画像枚数・先頭画像を一覧で確認する。明確な商品分けを全件で繰り返し質問する必要はない。
5. 読めない形式の変換はメインが必要な画像だけ一時領域で行い、元パスと閲覧用パスを対応させる。元画像は変更しない。アプリへ渡す形式・画像上限は実装済みの契約に従う。

## 1.5 ブランドを引き、知らなければ調べて登録する

ブランドの特徴と強い系統は売れ方を大きく左右する。原稿を作る前に、商品ごとのブランドをアプリのブランドの表（AIだけが参照する知識）で引く。同じブランドの商品が複数あっても調査は1回にまとめる。

1. タグ・ロゴ・ユーザーの補足からブランド名を読み取り、`GET /api/v1/brands?q=<名前>` で引く（表記・カナの揺れは吸収される）。ブランドが読み取れなければ質問に回す。
2. 登録がない、または特徴・系統・`verifiedAt` が欠けていれば調べる。
   - ユーザーのヒントがあれば最初の手がかりにする。
   - Web検索（検索とページ取得）で、公式サイト・ブランドの解説・古着店の説明・同ブランドの売れている出品を読む。ブラウザは起動しない。検索で足りず、メルカリの検索結果など画面表示が必要な情報を見たいときは、トークンを多く使うため、開く前にユーザーに確認する（了承後は共通入口 `.claude/shared/cyk-browser-operations.md` に従う）。
   - 引き出す内容：読み方・別表記、国・年代・運営会社、特徴（作り・素材・ロゴ・定番商品）、一般的な使われ方と強い系統（アメカジ・ストリート・アウトドア・平成/お兄系・y2k など）、売れている出品で使われている語句。
3. 事実ごとに出どころ（URL か `user`）と確かさ（`confirmed` 公式・複数の資料で一致／`likely` 1つの資料／`unverified` 推測）を付ける。根拠のない評判（「知る人ぞ知る」等）は事実にしない。
4. 候補をユーザーに短く提示し、了承・修正を受けて `PUT /api/v1/brands` で登録する（ユーザーが確認した場合は `verified: true`）。調べても分からなければ、分からないと記録して進める。
5. ユーザーが参考の出品URLを渡したら、タイトル・価格・使われている語句を `POST /api/v1/references` に残す（本文は保存しない）。次回、同じブランド・カテゴリーの原稿で `GET /api/v1/references` から引いて使う。

## 2. 商品担当へ原稿作成を割り当てる

担当定義の原本は `~/src/github.com/cyokodog/claude-config/.claude/agents/cyk-mercari-item-preparer.md`。実行中の環境で提供されているサブエージェント機能を使い、原本の役割と入力・出力を適用する。Claude固有の呼び出し名がCodexにも存在すると仮定しない。

- 1担当につき1商品。商品ID、担当画像だけ、商品に対応したユーザー補足、既存原稿・確認済みの回答・調査結果、その商品のブランドの知識（`brandKnowledge`：概要・系統・キーワード・事実と確かさ）と関係する参考出品の語句だけを渡す。全会話や全商品の画像を複製しない。
- 同時実行は最大2商品を初期値とし、環境の同時実行枠が少なければ減らす。大量の商品も一度に全員を起動せず、終わった枠で次を処理する。
- 担当が利用できなければ、担当未実行と報告し、その割当工程で停止する。実行したことにして続けない。
- 同一商品を再開する場合は、既存原稿と新しい回答を渡す。ユーザーが確定した内容を作り直したり、調査済みのURLを毎回読み直したりしない。原稿が競合したら古い結果で上書きせず差分を確認する。
- 商品担当がブラウザを共有して調査する構成にはしない。追加調査が必要なら依頼項目をメインへ返す。

## 3. 質問を集約し、対象商品へ回答を戻す

- 担当の結果を商品IDで照合し、画像の観察・ユーザー確認済み・資料で確認済み・仮説を区別する。
- 商品名や型番、状態、付属品などの未確認事項を、商品IDごとに短くまとめてユーザーへ聞く。画像の不足や撮り直しも、この段階で伝える。
- 全商品に共通する回答は、ユーザーが全商品への適用を明言した場合のみ共有する。「ケーブルあり」などを別商品へ流用しない。
- 回答は該当する商品担当へ戻し、質問が解決した範囲で原稿を更新する。待っている商品のために、無関係な商品の準備を止める必要はない。
- 商品の同定に資料確認が必要な場合は、同梱の [原稿・調査ガイド](references/content-guidelines.md) に従う。通常取得で足りない場合の閲覧は `.claude/shared/cyk-browser-operations.md` の共通入口を使い、同じブラウザの操作はメインが直列に行う。

## 4. 原稿をアプリ内に保存する

保存APIが実装済みの場合だけ行う。画像の管理用コピーや原稿の永続化はアプリに任せ、スキルからアプリの内部データファイルを直接編集しない。

APIの `revision` を担当への `baseRevision` として渡す。既存商品の管理画像を担当が読めない場合は、認証済みの画像取得APIから一時領域へ取得し、商品ID・画像ID・順序を維持して担当へ渡す。内部保存パスを推測しない。担当が返す `categoryCandidate` は提案であり、実装済みカテゴリー検索でIDを解決してからAPIの `category` へ対応付ける。IDが未収録なら候補名を残す保存までとする。

接続キーはアプリの設定で指定された場所から必要な処理へだけ渡し、会話・ログ・原稿・URLに書き出さない。APIの成功応答を読み戻して、商品ID・原稿の版が一致するか確認する。

原稿の準備とメルカリ反映は別々に管理する。担当が原稿を返したことを反映成功と混同しない。

| 軸 | 値 | 意味 |
| --- | --- | --- |
| `preparationStatus` | `images_only` | 画像のみ。原稿の準備前 |
|  | `needs_confirmation` | 原稿案はあるが不明点・ユーザー確認が残る |
|  | `ready` | 5項目がそろい、必要な確認が済んでいる |
| `reflectionStatus` | `not_started` | メルカリへの入力は未着手 |
|  | `running` | アプリが入力中 |
|  | `succeeded` | 対象5項目の入力と読み戻しを確認 |
|  | `partial` | 一部の入力が失敗・未完了 |
|  | `unknown` | 接続切れなどで実際の結果を確認できない |

この表は合意した状態の意味。実際のAPIでのフィールド名・値は契約を確認する。入力許可は準備状態と分け、`ready` だけでメルカリ入力を始めない。

- 未完成の原稿もアプリ内に保存できる契約なら、未確認箇所を残して保存する。原稿保存の成功応答と保存された版を確認してから「アプリ内に保存」と報告する。
- 保存失敗なら、会話中の案と保存済みの原稿を区別して伝える。画面案の「保存済み」表示を実データ保存の証拠にしない。
- 原稿を修正したら新しい版として扱い、古い版への承認や過去の反映成功を新しい版へ流用しない。過去の入力結果は対象の版に結びついた履歴として残し、現在の原稿が反映済みかを別に示す。
- 原稿の提案・修正は、変更項目だけでなくその商品の5項目全体を提示する。他商品の全文まで毎回再掲する必要はない。

## 5. 承認済みの商品を1件ずつ入力する

入力APIが実装済みで、対象商品・原稿の版・対象タブへの入力が承認されている場合だけ行う。

1. 接続・認証・対象タブ・カテゴリーのIDとアダプターの検証状態を、実装済みAPIで確認する。カテゴリーは保存済みの一覧を検索し、名前からIDを推測しない。一覧がない・一致しない場合は未解決として返す。
2. 承認された商品と原稿の版を指定して依頼する。同じタブへの操作は常に1商品ずつ。複数商品の準備が並行していても、商品担当から入力APIを呼ばせない。
3. 処理IDで結果を取得し、画像・商品名・カテゴリー・状態・説明の各結果と読み戻しを確認する。依頼受付は反映完了ではない。
4. 再送は契約にある重複防止キーを使う。入力のみ（`mode: "fill"`）はアプリが出品画面を空にしてから入力し直すため、ユーザーの指示があれば同じ版を上書きで再入力できる。下書き保存（`mode: "draft"`・一括処理）は下書きの重複を作るため、`partial`・`unknown` の後に自動で再実行しない。原稿を変更したら、承認対象の版も見直す。
   - 入力の依頼そのものがその版の承認として記録される。`/approve` の呼び出しは不要。
5. 商品を切り替える前に、前の商品が未保存のフォームへ残っていないか、アプリが安全に区切れるかを確認する。前の商品の内容を上書きしてよいと推測しない。複数商品の連続入力やメルカリ下書き保存が未実装なら、1件の引き渡しで止まる。

終了時は、商品IDごとに「会話中の原稿／アプリ保存済み」「準備状態」「反映状態・未完了項目」を短く報告する。成功した商品の原稿作成までやり直さず、次回は未完了の商品と工程だけを再開する。
