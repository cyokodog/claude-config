# cyk-gh-flow-lite

個人プロジェクト向けの一気通貫モード。ユーザーとの相談で方向が決まったら、AI が Issue にまとめ、承認を得て実装し、**AI 自身が可能な限り動作検証まで行い**、承認を得て記録・commit からマージまで一気に流す。

このスキルの性質:

- **Issue を先に作る** — ブランチ名に番号が要るため。中身は厳密でなくてよく、作業しながら更新・コメントで育てる
- **承認は 2 回だけ** — Issue を作る前と、マージの前
- **途中の相談は自由** — 実装中に方針の相談や見た目の確認が要れば、その場で止まって聞いてよい
- **学びを使い捨てない** — 経緯は Issue と `docs/issues/<N>/` に、知見は `docs/knowledge/` と claude-config に残す（後述）

仕事のプロジェクトには使わない（そちらは PJ 側の AI 定義に従う）。

## 使ってよい場面かの判断

このスキルは承認後に**マージまで自動で実行する**。マージは取り消せない操作なので、個人プロジェクト（`gh repo view --json owner` のオーナーが `cyokodog`）でない場合は、**マージ手順に入る前に**「このリポジトリでマージまで回してよいか」を一度確認する。

ユーザー全体指示に「明示的な指示がない限り commit / push しない」があるが、**このスキルの起動自体がその明示的な指示にあたる**。承認ゲートを通過したら commit / push / マージで止まらずに進む。

## 手順

### 1. 起点の解決

`$ARGUMENTS` と会話を見て判断する。

- **Issue 番号または URL** → `gh issue view <N> --json number,title,body,url,comments` で読み、手順 3（ブランチ作成）へ進む
- **それまでの相談の結論、または文章での依頼** → 手順 2 で Issue にする
- **引数も相談もない** → ユーザーに何をするか聞く

### 2. Issue の下書きと作成（承認ゲート 1）

相談の内容から Issue の下書きを作り、**会話で見せて承認を得る**。厳密でなくてよい。ポイント見積もりや Project への登録はしない（仕事用の `cyk-gh-issue-create` は使わない）。

```markdown
## 背景
<なぜやるか。相談で出た不満・要望を短く>

## 決めたこと
<相談で合意した方針。採らなかった案とその理由があれば一言>

## やること
- [ ] ...

## 完了条件
- ...
```

- タイトルは何をするかが分かる短い日本語
- 実装に必要なコードの読み込みはこの前に済ませ、方針が妥当か確かめておく

承認されたら作成する。この承認を**実装開始の承認**も兼ねる。

```bash
gh issue create --title "<タイトル>" --body "<本文>"
```

### 3. main を pull してブランチを切る

```bash
DEFAULT=$(gh repo view --json defaultBranchRef --jq '.defaultBranchRef.name')
git status --short            # 未コミットの変更があれば、扱いをユーザーに聞く
git checkout "$DEFAULT" && git pull
git checkout -b "feat/#<N>-<短い英語のスラッグ>"
```

ブランチ名は `git branch -a` で既存の命名規則を確かめ、合わせる。

### 4. 実装

- 関係しそうなナレッジを先に見る: プロジェクトの `docs/knowledge/README.md` と `~/src/github.com/cyokodog/claude-config/knowledge/README.md`
- 実装中に方針の相談・見た目の確認が要るなら、その場で止まって聞いてよい。決まったことは Issue に反映する（下の「記録の残し方」）
- 本番で動いているもの（ローカルのサーバー、実データ）を検証で壊さない。別ポート・別データ・スクラッチパッドで確かめる

### 5. 動作検証（AI 自身が可能な限りやる）

**ここがこのスキルの主要な仕事。** 「実装したので確認してください」で丸投げしない。上から順に、できるところまで自分でやる。

1. **型チェック・ビルド** — `npx tsc --noEmit`、`npm run build` 等（プロジェクトに応じて）
2. **既存テスト** — テストスクリプトがあれば実行する
3. **E2E（Playwright）** — UI 挙動が絡む変更なら、実際にブラウザを動かして確認する。**Playwright が未導入なら、断らずにインストールしてよい**（`npm i -D @playwright/test && npx playwright install chromium`）
4. **その他の手段** — CLI なら実際に叩く、API なら curl で叩く、スクリプトなら実行する。手段は問わない

E2E で導入したものの扱い（既定）:

- `package.json` / lockfile / `playwright.config.ts` / spec ファイルは **PR に含める**
- `test-results/` `playwright-report/` は `.gitignore` に追加する
- 使い捨ての確認用スクリプトはスクラッチパッドに置き、リポジトリに残さない

**ハマった場合:** 同じ問題で修正 → 再検証を **3 回**繰り返して抜けられなければ、そこで止まる。試したこと・症状・差分の状態をまとめて報告し、判断を仰ぐ。

### 6. 承認ゲート 2（マージ前）

**commit の前に行う。** 報告する内容:

- 何を変えたか（ファイルと要点）
- **どう検証して、何が確認できたか**
- **AI では検証できなかった点**（実機での見た目、拡張機能の読み込み、外部サービス連携など）
- **記録とナレッジの案**: 何を、どこに書くか（下の「記録の残し方」「ナレッジの残し方」に従った仕分け）

ユーザーの OK が出たら手順 7 以降を**止まらずに一気に実行する**。ユーザーの確認待ちの点（実機での見た目など）があり、それを見てからマージしたいと言われたら待つ。

### 7. 記録・ナレッジを書いて commit

1. 承認された案に従って、Issue の更新・コメント、`docs/issues/<N>/worklog.md`、`docs/knowledge/`、claude-config を書く
2. `git status --short` で、`.env` 系や実行時の状態ファイルなど**コミットすべきでないものが混ざっていないか**確認する
3. commit する。メッセージは `git log --oneline -20` の慣習に合わせる。粒度は規模に応じて決める（小さければ 1 つ、大きければ意味のまとまりごと）

claude-config に書いた場合は、claude-config 側でも commit して push する（main に直接 commit する運用）。ユーザーの作業中の未コミットの変更が claude-config にあれば、それには触らず自分が書いたファイルだけ commit する。

### 8. PR 作成

```bash
git push -u origin HEAD
gh pr create --base "$DEFAULT" --title "<タイトル>" --body "<本文>"
```

本文は `refs #<N>`（完了するなら `closes #<N>`）で始め、何を変えたかと、**どう検証したか**を数行。詳しい経緯は worklog へのリンクで済ませる。

### 9. マージ

```bash
gh pr merge <PR番号> --squash --delete-branch
```

- マージ方式はリポジトリの設定に従う（`--squash` が使えなければ `--merge`）
- **必須チェック（CI）がある場合は `--auto` を付け**、完了を待つか「自動マージ予約済み」と報告する
- 自動モードの判定で止められたら、`~/.claude/settings.json` の `permissions.allow` に `Bash(gh pr merge:*)` があるか確かめ、なければユーザーに伝えて止まる（迂回しない）

### 10. main に戻って pull

```bash
git checkout "$DEFAULT" && git pull
git branch -D <作業ブランチ>
```

squash マージ後のローカルブランチは未マージ扱いになるため `-D` を使う。

### 11. 結果の報告

- Issue と PR の番号・URL、マージ済みか（`--auto` なら予約済みか）、Issue が閉じたか
- 変更したファイルと実施した検証
- 書いた記録・ナレッジの場所

## 記録の残し方（Issue と docs/issues/<N>/）

作業の記録は **Issue と `docs/issues/<N>/worklog.md` の両方**に残す。会話が消えても、別セッションで続きができる状態にする。**どちらに何を書くかは内容の濃さで決める。**

| 書く場所 | 向いている内容 |
|---|---|
| **Issue 本文の更新** | 方針・やること・完了条件が変わったとき（本文は常に「今どうなっているか」を表す） |
| **Issue へのコメント** | 節目の短い報告: 方針を変えた・ユーザーと決めた判断・検証の結果・マージした、など。数行で済むもの |
| **`docs/issues/<N>/worklog.md`** | 長くなる経緯（すったもんだ）: 試して駄目だった方法とその理由、原因調査の過程、ハマりどころ、外部に残った成果物の在り処（URL・パス・ID）、未完の作業と次にやること |

- 判断の目安は「**別セッションの自分が、これを読んで続きをやれるか**」
- コメントに書いた内容を worklog に丸写ししない。長い経緯は worklog に書き、コメントからはその節へのリンクを貼る
- 規模に見合った量だけ書く。テンプレートを埋めるための中身のない項目は並べない
- worklog は Issue につき 1 ファイル。既にあれば追記する。同じディレクトリの実装計画（`index.md` 等）には触らない
- 途中で止まった場合も、そこまでの内容を残す（未完の申し送りこそ価値が高い）

## ナレッジの残し方

作業で得た学びのうち、この Issue を離れても役立つものは、ナレッジとして残す。

| 内容 | 置き場所 |
|---|---|
| そのプロジェクトで意味を持つ知見（仕組み、運用手順、決まりごと） | `docs/knowledge/<topic>.md`。目次 `docs/knowledge/README.md` に 1 行で要約を足す |
| プロジェクトをまたいで役立つ知見（ツールの罠、OS・ブラウザの挙動など） | `~/src/github.com/cyokodog/claude-config/knowledge/<topic>.md`。目次 `README.md` に足す |
| プロジェクトをまたいで守るルール | `~/src/github.com/cyokodog/claude-config/.claude/rules/<topic>.md`。新規なら `~/.claude/rules/` にリンクを張る（claude-config の CLAUDE.md の手順） |

- `docs/` 以下はディレクトリ名・ファイル名を英語、本文は日本語
- 1 テーマ 1 ファイル。既存のファイルに合うテーマなら追記する
- ルールは毎回読み込まれるので短く保つ。特定のファイルを触るときだけ効けばよいものは `paths:` で絞る
- 経緯（いつ何があったか）はナレッジに書かない。ナレッジは「次にどうすればよいか」だけを書き、経緯は worklog に置く

## 止まる条件

### 必ず止まる

- **承認ゲート 1**（Issue の作成前）と **承認ゲート 2**（commit の前）
- 個人プロジェクトでないリポジトリで、マージ前の確認が取れていない

### 異常で止まる

- 型チェック・ビルドが通らず、自力で直せない
- 検証で同じ問題に 3 回ハマって抜けられない
- コミット対象に `.env` 系など機密が混ざっている
- マージがコンフリクトした、または権限で止められた

止まった場合も、そこまでの内容で記録を残す。そのうえで現在の状態（ブランチ・未コミットの差分）を報告し、ユーザーの判断を仰ぐ。
