# cyk-gh-flow-lite

個人プロジェクト向けのカジュアルな一気通貫モード。実装方針を伝えてから実装し、**AI 自身が可能な限り動作検証まで行い**、検証が取れたらユーザーの承認を得て commit から マージまで一気に流す。

このスキルの性質:

- **事前の計画ファイルは作らない** — 方針は会話で伝えるだけ
- **確認は 1 回だけ** — 動作検証の報告後に集約する
- **1 コミット** — 粒度を分けない
- **1 セッションで完走** — 起動したらマージまで通す
- **やった結果を残す** — Issue 起点なら `docs/issues/<N>/` に作業ログを書く（後述）

壊れても自分が困るだけの規模の変更に使う。ステップごとに確認したい規模なら、このスキルは使わない。

## 使ってよい場面かの判断

このスキルは承認後に**マージまで自動で実行する**。マージは取り消せない操作なので、個人プロジェクト（`gh repo view --json owner,isPrivate` で自分がオーナー）でない場合は、**マージ手順に入る前に**「このリポジトリでマージまで回してよいか」を一度確認する。

なお、ユーザー全体指示に「明示的な指示がない限り commit / push しない」があるが、**このスキルの起動自体がその明示的な指示にあたる**。承認ゲートを通過したら commit / push で止まらずに進む。

## やらないこと

- 事前の実装計画ファイルの作成。方針は**会話で伝えるだけ**でファイルには書かない（作業ログは事後に残す）
- Issue の新規作成（Issue 起点の場合は既存のものを読むだけ）
- 実装中の逐次確認（承認ゲートは動作確認後の 1 回に集約する）

## 作業ログを残す

**Issue 起点の場合、扱った内容は規模の大小にかかわらず必ず残す。** 別セッションで続きをやる可能性があるため、会話が消えても再開できる状態にする。

### 置き場所

```
docs/issues/<N>/worklog.md
```

Issue につき 1 ファイル。**既にあれば追記する**（上書きしない）。同じ Issue で複数回作業した場合はセクションを足していく。

- `<N>` は Issue 番号。**Issue 起点でない場合は書かない**（置き場所が決まらないため）。ただし残しておく価値がありそうなら、その場でユーザーに相談する
- 同じディレクトリに実装計画（`index.md` 等）が既にあっても**触らない**。扱うのは `worklog.md` だけ

### 何を書くか

**内容は固定しない。** 一行で済む変更もあれば、外部ツールの成果物や込み入った判断が絡むものもある。**規模に見合った量だけ書く**。テンプレートを埋めるために中身のない項目を並べない。

判断の目安は「**別セッションの自分が、これを読んで続きをやれるか**」。それに要る情報だけ書く。

書く価値が高い順:

1. **セッションをまたいで失われる情報** — 最優先。会話にしか無いものは必ず書く
   - 外部に残った成果物の在り処（公開 URL、生成ファイルのパス、外部サービス上の ID など）
   - 未完で残した作業、次にやること
   - 試して駄目だった方法とその理由（同じ轍を踏まないため）
   - ユーザーとの間で決めた判断・前提
2. **何をやったか** — 変更の要点。差分を読めば分かることは詳しく書かない
3. **どう検証したか** — 実行したコマンドと結果。AI では検証できずユーザーに委ねた点があればそれも
4. **PR / マージの結果** — PR 番号と URL、マージ済みか

軽微な変更なら 1〜2 と PR 番号だけで十分。逆に `/design` のような外部成果物が出るスキルを経由した場合は、**URL と作業ファイルの場所を必ず書く**（それが無いと別セッションで続きができない）。

### いつ書くか

**手順 6（コミット）の直前**に書き、実装と同じコミットに含める。承認ゲートを通過した時点で内容が確定するため。

途中で止まった場合（型チェック失敗・検証ループ超過・ユーザーが中断など）も、**そこまでの内容でログを残す**。むしろこのケースこそ申し送りの価値が高い。作業ツリーが未コミットのままでよく、その状態もログに書く。

## 手順

### 1. 起点の解決

`$ARGUMENTS` を見て判断する。

- **Issue 番号または URL** → `gh issue view <N> --json number,title,body,url` で読み、これをやることの入力にする
- **それ以外の文章** → その内容をやることとして扱う
- **引数なし** → ユーザーに何をするか聞く

### 2. 実装方針の提示

必要なコードを読んだうえで、以下を**会話で簡潔に伝える**（ファイルには書かない）。

- 何を変えるか（対象ファイルと変更の要点）
- どう検証するつもりか（手順 4 の検証手段の見込み）

これは**通知であって承認待ちではない**。伝えたらそのまま実装に進む。ただし方針が複数に割れて選択がユーザー判断な場合、また既存設計を大きく変える必要が判明した場合は、そこで一度聞く。

### 3. ブランチ作成と実装

現在のブランチがデフォルトブランチ（`main` 等）なら、ブランチを切ってから実装する。既にトピックブランチ上ならそのまま使う。

```bash
gh repo view --json defaultBranchRef --jq '.defaultBranchRef.name'
git checkout -b <ブランチ名>
```

ブランチ名は既存の命名規則に合わせる（`git branch -a` で確認）。Issue 起点なら番号を含める。

### 4. 動作検証（AI 自身が可能な限りやる）

**ここがこのスキルの主要な仕事。** 「実装したので確認してください」で丸投げしない。上から順に、できるところまで自分でやる。

1. **型チェック・ビルド** — `npx tsc --noEmit`、`npm run build` 等（プロジェクトに応じて）
2. **既存テスト** — テストスクリプトがあれば実行する
3. **E2E（Playwright）** — UI 挙動が絡む変更なら、実際にブラウザを動かして確認する。**Playwright が未導入なら、断らずにインストールしてよい**（`npm i -D @playwright/test && npx playwright install chromium`）。検証用の spec を書いて実行し、期待どおり動くことを目で確認する
4. **その他の手段** — CLI なら実際に叩く、API なら curl で叩く、スクリプトなら実行する。手段は問わない

E2E で導入したものの扱い（既定）:

- `package.json` / lockfile / `playwright.config.ts` / spec ファイルは **PR に含める**（残す価値のある資産のため）
- `test-results/` `playwright-report/` は `.gitignore` に追加してコミット対象から外す
- 使い捨ての確認用スクリプトはスクラッチパッドに置き、リポジトリに残さない

**ハマった場合:** 同じ問題で修正 → 再検証を **3 回**繰り返して抜けられなければ、そこで止まる。試したこと・観測した症状・現在の差分の状態をまとめてユーザーに報告し、判断を仰ぐ。無言でループを続けない。

### 5. 承認ゲート

**このスキルで唯一の確認ポイント。** commit の前に行うので、この時点で作業ツリーは未コミットのまま。ユーザーが「やめる」と言えば git の巻き戻しは不要。

報告する内容:

- 何を変えたか（ファイルと要点）
- **どう検証して、何が確認できたか**（実行したコマンド・E2E の結果）
- **AI では検証できなかった点**があれば、それを明示してユーザーに確認を依頼する（例: 実機での見た目、外部サービスとの連携、認証が必要な画面）

ユーザーの OK が出たら手順 6 以降を**止まらずに一気に実行する**。

### 6. 作業ログを書いてコミット

Issue 起点の場合、まず「作業ログを残す」に従って `docs/issues/<N>/worklog.md` を書く（既にあれば追記）。

```bash
git status --short
```

`.env` 系など**コミットすべきでないファイルが混ざっていないか確認する**。混ざっていればそれを除外し、ユーザーに知らせる。

メッセージは `git log --oneline -20` で既存の慣習（prefix の有無・言語）を読み取って踏襲する。粒度は分けずに 1 コミットでよい。

### 7. PR 作成

```bash
gh pr create --title "<タイトル>" --body "<本文>" --base <デフォルトブランチ>
```

本文は簡潔に。何を変えたかと、**どう検証したか**を数行書く。Issue 起点なら `refs #<N>` を先頭に入れる。

### 8. マージ

```bash
gh pr merge <PR番号> --squash --delete-branch
```

マージ方式はリポジトリの設定に従う（`--squash` が使えなければ `--merge`）。

**必須チェック（CI）が設定されているリポジトリでは `--auto` を付ける**（`gh pr merge <PR番号> --squash --delete-branch --auto`）。チェック完了を待たずに叩くと弾かれるため。`--auto` にした場合は、マージが完了するまで待つか、「自動マージ予約済み」であることを報告する。

### 9. main に戻って pull

```bash
git checkout <デフォルトブランチ>
git pull
git branch -D <作業ブランチ>
```

squash マージ後のローカルブランチは git から見ると未マージ扱いになるため、`-d` ではなく `-D` を使う。

### 10. 結果の報告

一気に実行したため、**何をしたかをまとめて報告する**。

- 作成した PR の番号と URL
- マージ済みであること（`--auto` の場合は予約済みであること）
- 変更したファイル
- 実施した検証
- Issue 起点だった場合、その Issue が閉じたかどうか

## 止まる条件

### 必ず止まる

- **手順 5 の承認ゲート**（動作確認の報告後）
- 個人プロジェクトでないリポジトリで、マージ前の確認が取れていない

### 異常で止まる

- 型チェック・ビルドが通らず、自力で直せない
- 検証で同じ問題に 3 回ハマって抜けられない
- コミット対象に `.env` 系など機密が混ざっている
- マージがコンフリクトした

止まった場合も、Issue 起点なら**そこまでの内容で作業ログを残す**（未完の申し送りとして価値が高い）。そのうえで実行した内容と現在の状態（ブランチ・未コミットの差分）を報告し、ユーザーの判断を仰ぐ。
