# cyk-gh-flow

Issue を起点とした一連の作業の**現在位置を判定し、次の1ステップを提案・起動する**だけのスキル。

このスキルは**順序と現在位置しか持たない**。各ステップで何をどう書くかは個々のスキルの責務であり、ここには一切書き写さない（書き写すと二重管理になる）。

## 絶対の原則

- **自動で次のステップに進まない。** 1ステップ起動したら必ず戻ってきて止まる
- **自明であってもユーザーに確認する。** 状態から次が一意に決まる場合でも、起動前に必ず確認を取る
- 状態は**その場で導出する**。前回どこまでやったかを記憶・保存しない

## ステップの順序

```
①  cyk-gh-issue-create      Issue 起票
        ↓
②  cyk-impl-plan-create     実装計画 → docs/issues/<N>/
        ↓
③  cyk-gh-branch-create     ブランチ作成
        ↓
④  cyk-impl-from-plan       Step を順に実装・記録（Issue コメント）
        ↓  ←─────────────────────────┐
④.5 共通ブラウザ入口        E2E テスト（環境がある PJ のみ）
        ↓                                          │
⑤  （スキルなし）          動作検証をどうするか相談 │
        ↓                                          │ ❌/⚠️ や検証failで ④ に戻る
⑥  cyk-gh-pr-review        完了条件と差分の照合    │
        ↓                                          │
⑦  cyk-gh-pr-create        PR 作成 ────────────────┘
```

補足：

- **② が ③ より先**。計画作成はコードを読むだけで書き込まないため、ブランチ不要
- **⑤ は専用スキルを持たない相談ステップ**。実装が終わった（AI が判断した／ユーザーが判断した）段階の次に、**何をどう検証するかをユーザーと決める**。詳細は下記
- **⑥ が ⑦ より先**。`cyk-gh-pr-review` は `git diff origin/<BASE>...HEAD` を見るため PR 不要。名前に反して「Issue の完了条件と差分の照合」であり、PR を出す前のゲートとして機能する
- **⑥ はコード読解であって動作検証ではない**。差分を読んで完了条件と照合するだけで、実際には動かさない。だから ⑤ が別に必要
- **⑥ で修正が入ったら、⑦ に進む前に記録との整合を確認し、続けてコミットを提案する**。`cyk-gh-pr-review` は修正しないが、レビュー結果を受けた修正は計画ファイル・Issue 本文に波及する。記録の追従まで済んだ時点がコミットの区切りになる。詳細は下記「⑥ の後、⑦ に進む前の確認」
- **⑥ の前にコミットが必要**。`cyk-gh-pr-review` は `git diff origin/<BASE>...HEAD` を見るため、未コミットだと差分が空になり「実装が見当たらない」と誤判定する。コミットのタイミングはユーザーが決めるので、**⑥ を提案する前に未コミットの変更が無いか確認し、あればユーザーに知らせる**（コミットを代行しない）
- **④.5 は E2E テスト環境があるプロジェクトでのみ通る**。無いプロジェクトでは飛ばす。詳細は下記
- **① は直線の先頭専用ではない**。作業中に残課題を別 Issue に切り出す場合など、どのステップからでも脇に呼べる（`cyk-impl-from-plan` も残課題で `cyk-gh-issue-create` を呼ぶ）

## ④.5 E2E テスト（環境があるプロジェクトのみ）

**E2E テスト環境が無いプロジェクトでは、このステップごと飛ばす。** 環境の有無は実際に確認して判断する。

```bash
ls -d e2e tests/e2e 2>/dev/null
find . -maxdepth 2 -name 'playwright.config.*' -not -path '*/node_modules/*' 2>/dev/null
grep -l '@playwright/test' package.json 2>/dev/null
```

いずれも空なら E2E 環境なしと判断し、⑤ に進む。

環境がある場合、④ の実装内容に対して E2E テストを追加・更新すべきかをユーザーと相談する。テストを書く場合は `~/src/github.com/cyokodog/claude-config/.claude/shared/cyk-browser-operations.md` の共通入口を使う。SPAは目的 `spa-e2e`、それ以外は `e2e` とし、入口が返すスキルを起動する。ツールや環境別の呼び先はこのフロー内に持たない。

入力は呼び先スキルの指定に従う（ファイル名・テスト内容・URLなど）。

E2E のコードは実装の一部なので、⑤ の動作検証・⑥ のレビュー・コミットの対象に含める。

## ⑤ 動作検証をどうするか相談する

対応するスキルが無く、このスキル自身が担当する唯一のステップ。

**なぜ独立させるか。** 検証内容は計画時点では決まらない。実装してみて初めて「何を確かめるべきか」が分かる（実例: Issue #33 は Step 5 の動作確認で新たな不具合が2件見つかり、Step 6 が追加された）。計画に書いた検証項目をそのまま実行するのではなく、**実装が終わった時点で改めて相談して決める**。

進め方：

1. **実装が完了したという判断を確認する**。AI が判断した場合もユーザーが判断した場合も、ここで一度明示する
2. **検証の材料を集めて提示する** — Issue 本文の完了条件、実装で変更した箇所、Issue コメントに記録された「実測で判明した点」など
3. **何をどう検証するかをユーザーと決める**。以下を必ず確認する
   - 手作業が必要か（ローカル起動・外部サービスの操作・環境変数の差し替えなど）
   - 失敗させる検証が必要か（エラーハンドリングが完了条件に含まれる場合）
   - Issue 本文に検証手段が書かれていればそれを使う（例: Issue #23 の「失敗のさせ方（動作検証用）」）
4. **決まった内容を実施する。まず AI 自身が可能な限り検証する** — 「実装したので確認してください」で丸投げしない。上から順に、できるところまで自分でやる

   1. **型チェック・ビルド** — `npx tsc --noEmit`、`npm run build` 等（プロジェクトに応じて）
   2. **既存テスト** — テストスクリプトがあれば実行する
   3. **E2E** — ④.5 でテストを書いた場合は実行する
   4. **その他の手段** — CLI なら実際に叩く、API なら curl で叩く、スクリプトなら実行する

   そのうえで**手作業が必要な部分**（実機での見た目、外部サービスとの連携、認証が必要な画面など）はユーザーに依頼して完了を待つ

5. **AI では検証できなかった点があれば明示する。** 何を確認できて何を確認できていないかを区別して報告する
6. 検証で問題が見つかったら ④ に戻る。追加対応が計画の Step として必要なら計画mdに追記する

**ループの上限。** 同じ問題で ④ ↔ ⑤ を **3 回**繰り返して抜けられなければ、そこで止まる。試したこと・観測した症状・現在の差分の状態をまとめてユーザーに報告し、判断を仰ぐ。無言でループを続けない。

検証結果の記録は `cyk-impl-from-plan` の記録ルールに従う（Issue コメントに残す）。ここに記録の書き方は書かない。

## ⑥ の後、⑦ に進む前の確認

`cyk-gh-pr-review` はレビューするだけで修正しない。だが実際にはレビュー結果を受けて実装を直すことが多く、**その修正は記録に波及する**。⑥ で修正が入った場合、⑦ に進む前に記録との整合を確認する。

- **計画ファイル（`docs/issues/<N>/`）** — 実装と食い違っていないか。特に**コード片を載せている箇所は陳腐化しやすい**。計画ファイルは「現時点の正」なので、実装に合わせて上書きする
- **Issue 本文の完了条件** — レビュー修正で完了条件の意味が変わっていないか。変わっていれば上書きする
- **Issue コメント** — 原則**直さない**。コメントは時系列のトレースであり、「実装した → レビューで直した」という経緯が残るのが正しい。ただしコメントの記述が実装と食い違って**誤りになっている**場合は、レビュー修正を記録するコメントを新たに追記して打ち消す（`cyk-impl-from-plan` で1コメントにまとめる方針を採った場合の扱いは、そちらの記録ルールに従う）

修正が入らなかった（レビューが全て ✅ だった）場合は、この確認は不要。

### ナレッジを整理して保存する（レビュー修正の有無によらず実施）

⑥の結果を反映したら、⑦のPR作成前に `~/src/github.com/cyokodog/claude-config/.claude/shared/cyk-knowledge-recording.md` の共通手順で、知見の抽出・仕分け・保存案の提示を行う。承認された内容を保存し、目次を更新する。再利用できる知見がなければ「追加する知見なし」と報告する。上の記録整合確認を省略できる場合も、ナレッジの確認は省略しない。

保存した差分は下のコミット提案に含める。これにより⑦を自動起動せず、既存の確認・1ステップごとの停止を維持する。

### 記録の追従まで済んだら、コミットを提案する

レビュー修正と記録の追従が終わった時点が、コミットの区切りになる。⑦ に進む前に**コミット粒度とコミットメッセージを提案する**。

`git status --short` と `git diff` で未コミットの変更を把握し、以下の形で提示する。

```
## コミット提案

### 1. <メッセージ1行目>

<変更ファイル>

<必要なら本文で補足>

### 2. <メッセージ1行目>

...
```

粒度の決め方：

- **関心事ごとに分ける。** 1コミットが1つのことを説明できる単位にする。Step 単位とは限らない（複数 Step が同じ関心事なら1つにまとめてよいし、1 Step が複数の関心事を含むなら分ける）
- **リファクタと機能変更を混ぜない。** 挙動が変わらない整理と、挙動が変わる修正は別コミットにする
- **`docs/issues/<N>/` の計画ファイルは実装と同じコミットに含めない。** 記録であって実装ではないため、独立したコミットにする
- 未追跡ファイルのうち、**コミットすべきでないもの（`.env` 系など）が混ざっていないか確認し、あれば指摘する**

メッセージは対象リポジトリの既存の慣習に合わせる。

```bash
git log --oneline -20
```

prefix（`feat:` `fix:` 等）の有無・言語・粒度を実際のログから読み取って踏襲する。**独自の様式を持ち込まない。**

提示したら「**この粒度・メッセージでコミットしてよいですか？**」と承認を求める。承認されたらそのまま実行してよい。修正指示があれば反映して再提示する。

**承認を得ずにコミットしない。** 提案が自明に見えても必ず確認を取る。

## 手順

### 1. Issue 番号の解決

`$ARGUMENTS` から Issue 番号または URL を解決する。

1. 引数に番号・URL があればそれを使う
2. なければカレントブランチ名から推測する（例: `feat/#42-xxx` → `42`）
3. 推測できなければユーザーに確認する

`$ARGUMENTS` に開始ステップ番号（①〜⑦ または 1〜7）が併せて指定されている場合は、**状態判定をスキップしてそのステップを提案する**（Step 3 へ）。

### 2. 現在位置の判定

以下をその場で実行して状態を導出する。判定結果は保存しない。

```bash
# 未コミットの変更（⑥ の前に確認する）
git status --short

# Issue の存在とタイトル
gh issue view <N> --json number,title,state,url

# 計画の有無（ディレクトリではなく index.md の有無で見る。
# 計画を作らないスキルが同じディレクトリに記録を置く場合があるため）
ls docs/issues/<N>/index.md 2>/dev/null

# ブランチの有無（issue 番号を含むブランチ）
git branch -a --list "*<N>*"

# PR の有無（本文の全文検索なので、無関係な PR が混ざりうる）
gh pr list --search "<N>" --state all --json number,title,state,url,headRefName
```

PR は `headRefName` が ③ で確認したブランチ名と一致するものを採用する。一致するものが無ければ「この Issue の PR は無い」と判定する（`--search` は本文の全文検索であり、単に `33` に言及しただけの別 PR が引っかかるため）。

計画が存在する場合は `docs/issues/<N>/index.md`（分割構成なら各ステップファイルも）を読み、Step の完了状況を数える。

```bash
grep -hcE '^#{1,2} Step .*✅' docs/issues/<N>/*.md   # 完了
grep -hcE '^#{1,2} Step '     docs/issues/<N>/*.md   # 全体
```

**完了マークは `## Step N:` 見出し行の末尾の ✅ のみで判定する。** 本文中の表のセルにも ✅ は現れるため、行頭が見出しであることを必ず条件に含める（単純な `grep ✅` では誤判定する）。

判定表：

| 状態 | 次の提案 |
| --- | --- |
| Issue が存在しない | ①（番号ではなく内容から起票） |
| `docs/issues/<N>/index.md` が無い | ② |
| ブランチが無い | ③ |
| 未完了の Step がある | ④ |
| Step 全完了・E2E 環境あり | ④.5（E2E を書くか相談。環境が無ければ ⑤ へ）|
| Step 全完了・PR 無し | ⑤（動作検証の相談）|
| ⑤ 済み・未コミットの変更あり | ⑥ を提案する前に、コミットが必要なことをユーザーに伝える |
| PR がある | 完了。追加作業があれば ④ に戻る |

**⑤ と ⑥ を実施済みかどうかは導出できない。** ⑤ は相談ステップで、⑥ の `cyk-gh-pr-review` は GitHub に何も書き込まないため、どちらも痕跡が残らない。

Step が全完了して PR が無い場合、既定では **⑤（動作検証の相談）を提案する**。ただし「検証は済んでいる」とユーザーが言えば ⑥ へ、「レビューも済んでいる」と言えば ⑦ へ進んでよい。**どこまで済んでいるかは推測せず、ユーザーに確認する。**

### 3. 現在位置と次の1手の提示

以下の形式で提示する。

```
## Issue #<N> <タイトル>

| # | ステップ | 状態 |
| --- | --- | --- |
| ① | Issue 起票 | ✅ #<N> |
| ② | 実装計画 | ✅ docs/issues/<N>/ |
| ③ | ブランチ | ✅ <ブランチ名> |
| ④ | 実装 | ⏳ Step 3/5 |
| ④.5 | E2E | — （環境が無ければ「対象外」）|
| ⑤ | 動作検証 | — |
| ⑥ | レビュー | — |
| ⑦ | PR 作成 | — |

**次の提案: ④ cyk-impl-from-plan**（残り Step 3〜5）

これで進めますか？
```

状態の記号は `✅`（完了）/ `⏳`（進行中）/ `—`（未着手）を使う。

**ここで必ず止まる。** ユーザーの承認を得ずにステップを起動しない。次が一意に決まる場合でも確認する。

### 4. 承認されたステップを起動する

⑦を起動する場合は、上記の共通ナレッジ保存の確認が済んでいるか先に確かめる。未実施ならPR作成前に行う。既に承認・保存済みの同じ内容は重複して保存しない。

`Skill` ツールで該当スキルを起動し、Issue 番号を引数として渡す。

| # | スキル | 渡す引数 |
| --- | --- | --- |
| ① | `cyk-gh-issue-create` | （Issue 番号は渡さない。起票内容をユーザーと詰める） |
| ② | `cyk-impl-plan-create` | `<N>` |
| ③ | `cyk-gh-branch-create` | `<N>` |
| ④ | `cyk-impl-from-plan` | `<N>` |
| ④.5 | 共通ブラウザ入口で選ぶE2Eスキル（SPAは `spa-e2e`、それ以外は `e2e`）。環境が無ければ飛ばす | 呼び先スキルの指定に従う |
| ⑤ | （スキルなし。このスキル自身が担当。上記「⑤ 動作検証をどうするか相談する」を実行） | — |
| ⑥ | `cyk-gh-pr-review` | `<N>`（終了後、修正が入っていれば上記「⑥ の後、⑦ に進む前の確認」を実行） |
| ⑦ | `cyk-gh-pr-create` | `<N>` |

起動したスキルが終わったら**このスキルに戻ってきて止まる**。続けて次のステップに進まない。ユーザーが「次」と言った時点で Step 2 からやり直す（状態を再導出する）。

## やらないこと

- 複数ステップの連続実行はしない（全自動化はこのスキルの目的ではない）
- 各スキルの手順・書き方の基準をここに書かない（個々のスキルの責務）
- 判定結果の保存・キャッシュはしない（毎回導出する）
- コミットは提案・承認を経てから実行する（承認なしにコミットしない）
- プッシュはしない
