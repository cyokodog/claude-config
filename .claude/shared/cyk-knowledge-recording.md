# 開発フロー共通のナレッジ保存

通常の `cyk-gh-flow` と `cyk-gh-flow-lite` は、この手順で知見を抽出・仕分け・保存する。作業の経緯を残す既存のIssue・計画・worklogの手順とは区別し、各フローの承認・停止条件を維持する。

## 1. 候補を抽出する

会話、Issueコメント、実装・検証・レビューの結果から、次回の作業で再利用できる知見を拾う。対象は再現条件、原因と対処、ツールの制約、手順や設定の注意点、設計判断の適用条件など。

- 実際に確認した事実を根拠にする。推測・未検証の内容は確定事項として残さない。
- そのIssueの進捗や試行錯誤の時系列は既存の作業記録に残す。ナレッジには、次にどう判断・実行すればよいかを条件とともに書く。
- 再利用できる新しい知見がなければ「追加する知見なし」と報告し、ファイルを埋めるために作らない。

## 2. 保存先を決める

| 内容 | 保存先 |
| --- | --- |
| そのプロジェクトに固有の知見 | 対象プロジェクトの `docs/knowledge/<topic>.md`。目次は `docs/knowledge/README.md` |
| 個人プロジェクトから得た、プロジェクトをまたいで役立つ知見 | `~/src/github.com/cyokodog/claude-config/knowledge/<topic>.md`。目次は同ディレクトリの `README.md` |
| プロジェクトをまたいでAIが守るべき行動ルール | `~/src/github.com/cyokodog/claude-config/.claude/rules/<topic>.md`。追加・改名・削除時はこのリポジトリのリンク維持手順も実施する |

`topic` は知見の題材を表す英語のファイル名。既存の目次と該当ファイルを読んで、同じ題材なら追記・更新する。本文は日本語、原則1テーマ1ファイル。同じ内容を複数の場所へ丸写しせず、必要なら参照を置く。

仕事のプロジェクトでは、そのプロジェクトのAI定義と情報の保存範囲を優先する。個人用の横断ナレッジやルールへ持ち出すことを、この手順だけで許可されたとみなさない。機密・認証情報・個人情報は保存しない。

会話からのブログ投稿や技術tipsへの保存はこの共通処理では行わない。既存の記事・メモを移動・削除する処理でもない。

## 3. 各フローの確認タイミングで提示する

候補ごとに、何を残すか・根拠・保存先・新規か更新かをユーザーに提示する。ファイルへの書き出しは承認された範囲で行う。既にその内容・保存先の承認があれば、同じ確認は繰り返さない。

- **通常版**：⑥のレビュー結果と修正を反映した後、⑦のPR作成前に実施する。レビュー修正がなくても省略しない。⑥実施済みとして直接⑦へ進む場合も、この確認が済んでいるか確かめる。保存した差分をコミット提案に含め、既存の⑦起動前の承認と1ステップごとの停止を維持する。
- **ライト版**：手順6の既存の承認ゲートで記録・ナレッジ案として提示し、承認後の手順7で保存する。新しい承認ゲートは増やさない。

## 4. 保存と確認

承認された内容を保存し、必要な目次を作成・更新する。既存の関連知見を無関係に消さない。ルールを追加した場合はリンクも検証する。

完了時は、実際に保存したファイルと知見の要点を報告する。書けなかったものや未承認のものを保存済みと報告しない。中断時は候補と未保存の状態を引き継ぐ。

この処理自体はcommit / pushを許可しない。各フローとユーザーの明示的な指示に従い、設定リポジトリなど別リポジトリへのコミットも許可範囲を確認する。
